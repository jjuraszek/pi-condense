# Per-request image cap

Date: 2026-09-24
Status: approved for planning

## Context

Every image a model sees stays in the session transcript: a `read` of a PNG returns an `image` content block inside a `toolResult`, and pi replays the whole branch on every request. Pruning does not bound this - a summarized batch drops its images only once it is flushed, and a session with `enabled: false` never drops them.

Providers cap images per request. Measured 2026-09-24: a session that had read 31 images got `400 BadRequestError ... Too many images in request: 31 > 30` from an OpenAI-compatible gateway on every following request, so the session could not continue, and resuming it replays the same transcript into the same rejection.

## Problem

Nothing keeps the image count of an outgoing request under the provider's limit. The failure is deterministic once the transcript crosses the limit, and it surfaces as a hard request error rather than degraded context.

## Idea

| # | Decision | Rationale |
|---|---|---|
| 1 | `maxImagesPerRequest: number \| null`, default `null` (off). | Opt-in; zero behavior change for every existing config. |
| 2 | When set and a request carries more than N `image` blocks, the `context` handler replaces the oldest ones with a `text` block naming the omission, in steps of `ceil(N / 2)`: it omits `ceil((total - N) / step) * step` images. | Newest images are the ones the model is working with; a text note tells the model an image existed and how to get it back. Omitting one image per new image would rewrite the prompt prefix on every request past the cap and defeat provider prompt caching; stepping changes the prefix once per `step` new images. |
| 3 | The cap runs after pruning and independent of `enabled`. | It is a request-validity guard, not a context-economy feature: a session with pruning off must not be left unable to send. |
| 4 | Request-local only: the handler returns a new messages array and never mutates `event.messages` or the session file. | The transcript keeps every image; re-reading the file shows it again. |
| 5 | Validated finite and `>= 1`, floored to an integer; any other value resets to `null`. Config-file-only, no `/pruner settings` row. | Matches `frontierGapThresholdTokens`; `0` would strip every image, which is `images.blockImages` in pi itself. |

### Non-goals

- No per-provider limit table: the operator sets the number for the models they use.
- No image archiving or `context_tree_query` recovery path: the original stays in the session and on disk.

## Testing approach

Unit tests for the pure `capImages(messages, max)`: oldest images omitted in steps of half the cap across messages and within one message, the omitted set stable for image counts inside one step, older blocks replaced in place with the note, input arrays untouched, `undefined` returned when nothing changes, `null`/unset is a no-op. Config tests for `normalize` of valid, zero, negative, fractional and non-numeric values.
